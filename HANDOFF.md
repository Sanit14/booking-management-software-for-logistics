## Things to know (new in 1.7)
- **First CI run (push of `f4c5a67`) failed in `npm run check` on `keeper/dataRoot.test.ts` "refuses a bare drive"**: on the runner the checkout is on `D:\a\...`, and `win32.resolve('D:')` means "the current folder on D:", so `D:` passed as a data root. Fixed in `keeper/dataRoot.ts` (`resolveRoot`) with a cwd-independent test; `check` is 96 node + 70 database tests afterwards (commit `adde696`).
- **An older installer run over a newer install does not downgrade the files**: NSIS keeps the newer `Booking Manager.exe`/`app.asar` and only rewrites the uninstall registry entry, so the Settings "version" line can lie about what's actually running until you uninstall first. Always uninstall before installing an older build over a newer one.
- The main checkout needs its own `npm install` + `npm run postinstall` after a merge that adds a dependency (here, `electron-updater`) — the Stop hook runs `npm run check` in the main folder, not in a worktree.
- `npm run dev` started from the Bash tool leaves its Electron, keeper and vite running when the task is stopped, and a leftover dev Electron made a packaging run fail with `EPERM … rename win-unpacked.tmp` — stop them by hand (the keeper with `/shutdown`).
- `npm install --save-exact electron-updater@6.8.9` plus `npm run postinstall` takes ~12 min in a fresh worktree.
- Running `npm install` from inside a worktree's path while `--prefix`-targeting the main folder can add a stray `file:` self-dependency to the main `package.json`/`package-lock.json` pointing at the worktree; `git restore` fixes it, and removing the worktree afterwards leaves a dangling `node_modules` symlink to clean up.
- Backslashes in text typed through a shell heredoc can be collapsed; write files with the Write tool and check regexes and Windows paths afterwards. Edit scripts that rewrite a CRLF file must normalise to LF first, or lines end up with `\r\r\n`.
- Browser-pane check as in 1.5 (stub `window.bm`, now with `keeper.pins` and `update`); the pane's screenshots can lag, trust `get_page_text` and the stub's call log.

## Things to know (from 1.4)
- **Backups are rollback-journal files, not WAL.** `db.backup` copies the WAL flag; a read-only open of a WAL file leaves `-wal`/`-shm`, so `makeBackup` flips the temp copy to `journal_mode=DELETE` before verifying. The keeper switches it back to WAL when a restore is opened.
- A restore migrates the restored file without a fresh backup (the restored backup and the set-aside copy are both still in the folder).
- The clean-stop backup runs before the keeper exits, so `/shutdown` takes as long as a backup; the client's default timeout is 3 s (fine for a small database; the bridge's replace-old-keeper wait is 6 s). Revisit if the database grows to hundreds of MB. Same for the start-up backup vs the bridge's 10 s start wait.
- `listBackups` opens every backup read-only with `quick_check` (≤ ~78 files); fine in safe mode, do not call it on a hot path.
- `quick_check` runs at every start: O(database size).
- Hourly timer and the 5-minute marker timer are not covered by an end-to-end test (they need an hour / need records). The marker-raising end-to-end test promised for 2.1 still stands (insert via the first real endpoint, shorten the interval, assert the marker rose).
- Local-time names: if the PC clock is changed backwards, a new backup can share a name with an older one and replace it (same-minute names also replace each other: start + stop within a minute leave one file).

## Things to know (from earlier sessions, still true)

Bump it whenever routes or schema change.

- If the database cannot be opened for a reason other than damage (permissions, locked) the keeper logs `keeper-fatal` and exits 1; the screen says "could not be started (exit 1; see keeper.log)".

# Session 4.2 — plan (History page + the Admin settings left over)

## Primary goal
The owner can always answer "who did this, and when?": a **History** page lists everything that changed in the books in plain
sentences, searchable by seat, kind, action and LR / challan number, and shows old → new with names. Every PIN-gated action —
including five wrong tries — leaves a row there. In Settings the owner can also restore a backup while the app is running, move the
backup folder and rename a seat, each behind the Admin PIN and each visible in History; the developer Components card is gone from
the installed app.

## Phase 0 — What exists (read before building; reuse, invent nothing)
**How this serves the goal:** History is a *reader* of `audit_log` and the Settings items are small writes in the keeper's existing patterns, so nothing here needs a new table or a second way to check a PIN.

- **`audit_log`** (`keeper/migrations.ts:137`): `id, at (UTC ISO, ms), seat, action, entity, entity_id TEXT, before_json, after_json`; append-only triggers; **only index `(entity, entity_id)`** → the default "last 7 days, newest first" has no index → expect a scan → **migration v3** `CREATE INDEX audit_by_at ON audit_log (at)` (the card: only if EXPLAIN shows the scan; the EXPLAIN test is written first). `writeAudit` (`keeper/audit.ts`) is the only writer and needs a transaction. Existing readers: `lrs.history` (`keeper/lrs.ts:311`), `memos.history` (`keeper/memos.ts:538`) — both `ORDER BY at DESC, id DESC`, leave `print.%` out, resolve station names with `changesOf` (`keeper/lrRules.ts:157`). They stay as they are.
- **Every action code written today** (grep of `writeAudit`): `lrs.create|update|cancel|restore|memo-remove|memo-move|memo-add|memo-cancel` (entity `lrs`; create = the whole `lrs` row, update = only changed columns incl. `*_station_id`, `consignor_name`, `*_paise`, `stax_bp`) · `memos.create|edit|remove-lrs|move-out|move-in|add-lrs|recalculate|cancel` (entity `memos`; create has `truckId driverId fromStationId toStationId lrIds frozen`, the LR changes carry `lrNos`) · `wasuli.create|update|remove|assign|reassign|to-pool|collect|uncollect|remark` (entity `wasuli`; before/after = status, agent_id, dates, collected_paise, mode, remark; create / remove carry `lr_id`) · `masters.create|update|activate|deactivate` (entity = `stations|firms|trucks|drivers|agents`, before/after = the whole master row) · `pins.setup|change-system|change-admin|recover` (entity `settings`, id `pins`) · `settings.lr-defaults|company` · `print.memo|lr|firm|report` (entities `memos|lrs|firms|reports`).
- **Gaps against "every PIN-gated action appears":** a lock-out is only logged to `keeper.log` (`pin-refused`); `/pins/verify` (used by the updater's Install) writes nothing; installing an update is Admin-PIN gated but leaves no audit row; restore, backup-folder change and seat rename do not exist yet. - **Other seats:** keeper `seats.othersOnline` (45 s, `keeper/seats.ts`) + main's Windows process scan (`electron/processScan.ts`), combined in `assertNobodyElse` inside `electron/updater.ts:201` — private to the updater today.

## Decisions I took where the card is silent (change any before I build)
1. **The keeper resolves names, the screen writes sentences.** A History row carries the record's own fields (LR / challan number, the master's name *as in the row*), `changes[]` (field, from, to) with ids already turned into names, and a few facts (reason, agent, how printed…). Names come from batch joins on `entity` (an LR id, a memo id and a firm id with the same number can never meet). An id that exists only as an id in the row (a memo's truck / driver / stations) shows the **current master name**; a name stored in the row (LR consignor, a master rename) shows **as it was in the row**; the jump opens the current record.
2. **One table maps each known action code to a kind and a verb** (in `shared/`, data only). The filters turn into SQL on it; an unknown code is kind "other", is listed, and shows its raw code. Kinds: LR · memo · wasuli · firm · station · truck · driver · agent · PINs / settings · backup / restore · print. Verbs: created, edited, cancelled, restored, collected, undone, assigned, memo changes, activated, deactivated, locked out, printed (final list fixed by a test that every known code has both).
3. **Filters:** period (Last 7 days default, Today, This month, Last month, Custom), seat (any part of the name, ASCII case ignored), kind, action, LR no., Challan no. (`12` = this year, `12/2025` = that year). **LR no.** = that LR's own rows (including its memo take-offs / moves) and its wasuli rows while the collection exists; the row that *loaded* it is the memo's `memos.create`, found by **Challan no.** (it is one row per memo, not per LR). A removed collection's rows are not reachable by LR no. Prints are hidden unless "Show prints" is on or kind = print.
4. **Row behaviour:** one Tab stop per list (as Reports); Enter or a click opens the row's details (old → new, reason, who, which seat); the details carry an **Open LR 1248 / Challan 13 / the firm…** button, **Ctrl+Enter** does the same. Where each kind leads: LR → LR Entry view, memo → the memo, firm → Firm Accounts, wasuli → Wasuli page with that LR found (`Jump {to:'wasuli', no}`; this year's LR first, then last year's — the 3.4 quick-collect rule), station / truck / driver / agent → Masters with the row selected (`Jump` master kinds gain drivers and agents). PINs, settings, backup, seat and report rows have no record to open.
5. **Lock-outs:** the 5th wrong try writes `pins.locked` (`entity settings`, `after {kind}`, the seat) — written by `server.ts` after the route has answered, in its own transaction, because several PIN checks run inside a transaction that a refusal can roll back. Single wrong tries stay unlogged (the card). `makePins` gets an `onLocked(kind)` hook; the six `pin-refused` branches become one helper. Test-only env `BM_PIN_LOCK_MS` (like `BM_MARKER_REFRESH_MS`) shortens the 60 s lock so one test can lock out ~25 routes.
6. **Update install is audited** (inferred from "every PIN-gated action"): main calls a new keeper route `/settings/update-start` (Admin PIN, from / to version) right before it stops the keeper → audit row `app.update`. `/pins/verify` itself stays a pure check (no row on success, `pins.locked` on lock-out).
7. **Restore from Settings (normal mode):** one card "Restore a backup" opens a wide dialog with the *same* backup list and side-by-side preview as safe mode (extracted from `SafeMode.tsx` into one shared component). Apply needs the Admin PIN (checked by the keeper), **no other seat** (keeper's 45 s list *and* main's process scan, the scan lifted out of the updater into a shared helper that both use), makes a **fresh verified backup first and refuses the restore if that fails**, swaps the file (keeper closes its handle around `restoreFiles`, so `booking-before-restore-*` is kept), re-opens, migrates, writes audit row `backup.restore` (file, set-aside copy) into the **restored** database, publishes every table, and the screen reloads its status. Rows written after the backup was made are no longer in History (they are in the set-aside copy); the dialog says so.
8. **Backup folder:** Admin PIN → main's folder picker → keeper: absolute path; **same drive as the data root → refusal `backup-dir-same-drive`, the screen asks, "Use it anyway" resends with the confirm**; then a **verified backup is made in the new folder — that is both the "writable" check and the "backup at once"**; only on success the setting and audit row `settings.backup-dir` (old → new) are written and `backupDir` switches. Old backups stay where they were. An env override (`BM_BACKUP_DIR`) is only the start value for dev and tests.
9. **Seat rename:** Admin PIN → keeper route `/seats/rename` validates (2–20 characters, letters / digits / space / dash; not the name of another seat that **wrote to the audit log in the last 30 days or pinged since the keeper started**, case-insensitive — a seat that only reads and never pinged is unknown to us) and writes audit row `seat.rename` (from → to) → main then writes `seat.json`. **The new name is used from the next start** (the event stream, watchdog and updater hold the old one); the card says so. Old rows keep the old name by themselves.
10. **Components card** shown only when `!app.isPackaged` (main passes a `--packaged` argument, preload exposes `window.bm.packaged`); `npm run dev -- --components` still works. Settings' version card gets one line: the data folder is changed by the installer.
11. **Layout (1024 × 768, no page scroll):** History sits in the Admin group between Reports and Masters, no page header (as Reports): filter row, the list in its own scroll box (keyboard-scrollable), a details strip under the list, Load more. `KEEPER_VERSION` 16 → **17**, schema 2 → **3**.

## Phase 1 — History in the keeper (reads only), test first
**How this serves the goal:** this is where a row becomes "LR 1248 edited by PC03, consignee Ramesh → Suresh" — correct, ordered, paged and fast.
- `shared/keeper.ts`: `HistoryFilters`, `HistoryCursor {at, id}`, `HistoryRow`, `HistoryChange`, `HistoryPage {rows, next}`, the action → kind / verb table, `KeeperApi.history.list`, `KEEPER_VERSION = 17`.
- `keeper/migrations.ts` **v3** (index only; the 1.4 pre-migration backup runs by itself). Written *after* the EXPLAIN test that proves the scan.
- `keeper/historyRules.ts` (pure): `asHistoryFilters` (local dates → UTC bounds in the stored `at` format, seat ≤ 20, kind / verb from the table, `12` / `12/2025` parser, prints flag), `asHistoryCursor`. `keeper/history.ts` `makeHistory()`: one statement of fixed fragments (only values bound), `LEFT JOIN`s conditioned on `entity`, 101 rows read for 100 shown, then names resolved for the page only (a few point lookups). Route `/history/list`, bridge `keeper:history-list`, preload `history.list`.
- Tests: `historyRules.test.ts`; `history.dbtest.ts` — a hand-made log of every known action: order by `(at, id)`; each filter alone and combined; paging 100 / 101 / 250 (none twice, none lost); LR no. / Challan no. with and without a year; prints hidden / shown; names resolved (a station, truck, driver, agent, firm; **a renamed firm: older rows show the old name, the row's id is the current firm's**); an id shared by an LR, a memo and a firm never mixes; unknown action comes back with its raw code; a removed wasuli row still resolves its LR from the row; **EXPLAIN: the default filter, the seat filter and the LR / challan filters use an index and never scan `audit_log`** (before v3 this test is red, which is the card's proof); speed on 200,000 audit rows, first page < 100 ms (`fastest`); `migrations.dbtest.ts`: v3 on a v2 file keeps every row, makes a backup first, runs twice = no change; `server.test.ts`: the route answers, a bad body is 400, a read publishes no event, nothing from the log's text lands in `keeper.log`.
- Verify: `npm run check`; mutation checks (drop the `entity` condition of a join; drop the `print.%` default; cursor on `id` only) → a named test fails.

## Phase 2 — Lock-out rows and the PIN coverage proof
**How this serves the goal:** "every PIN-gated action appears in History" becomes a test that fails when someone adds a PIN route and forgets the row, instead of a promise.
- `keeper/pins.ts`: `makePins(now, onLocked?)` calls it once when the 5th wrong try starts a lock. `keeper/server.ts`: one `pinRefused(url, seat, r)` helper replaces the six `pin-refused` branches, drains the hook and writes `pins.locked` (kind, seat) in its own transaction. `BM_PIN_LOCK_MS` (tests only). Route list moves out of `route()` into `keeper/routes.ts` (`ROUTES`, no better-sqlite3, importable by the system-Node tests).
- `/settings/update-start` (Admin PIN, from / to) + `electron/updater.ts` calls it just before it stops the keeper; the audit row is `app.update`.
- Tests: `pins.dbtest.ts` (hook fires on the 5th try only, not on the 4th, not while locked, once per lock); **`server.test.ts` "PIN coverage"**: a table of every route that checks a PIN (system: masters update / set-active, lrs create-backdated / update / cancel / restore, memos create-backdated / edit / remove-lrs / move-lrs / add-lrs, wasuli uncollect / remark; admin: pins change-system / change-admin, settings set-lr-defaults / update-start / set-backup-dir, print set-company, memos recalculate / cancel, restore apply, seats rename; recovery: pins recover; pins verify = lock-out only) — for each: the right PIN → ok and a new row in `/history/list`; five wrong tries → `pin-locked` and a `pins.locked` row with the right kind and seat; and a **completeness guard**: every entry of `ROUTES` is in this table or in an explicit "no PIN" list, so a new route forces a decision.
- Verify: `npm run check`; mutation check (skip the hook in one branch) → the coverage test names that route.

## Risks worth knowing
- **Restore in normal mode** swaps the live file under a running keeper: the riskiest item; it is covered by a real-keeper test and refuses unless alone, PIN-checked, and backed up.
- `server.test.ts` PIN coverage drives ~25 routes with real scrypt checks: kept fast by `BM_PIN_LOCK_MS` and one shared fixture world.
- The updater loses its private process-scan helper to a shared one: no behaviour change intended, its flow has no automated test, so I will re-read it line by line after the move.

# Session 4.3 — Load test: 3 years of data, speed budgets, release 0.3.0

## Goal
Prove the app stays fast when the book is full: **3 years at the client's volume** (about 300 LRs a day, ≈ 330,000
LRs, their memos, wasuli and audit rows). Measure every budget from the Build Plan on this PC, fix whatever is slow,
make the speed tests stable, and ship **0.3.0** so the owner can measure the same on a real NComputing seat.

## Decided rules for this slice
**Generator (dev tool, never in the installed app)**
- `scripts/seed-load.cjs`: builds a database **through the keeper's own code** (the same `create` functions inside
  transactions, not hand-written SQL, so constraints, numbering, audit and frozen totals are real), into a throwaway
  data root given as an argument; refuses `C:\BookingManagerData` and any folder that already holds a `booking.db`.
- Realistic shape, fixed random seed (same file every run): 3 years ending today, Sundays light, Diwali week heavy;
  ~400 firms, 40 stations, 60 trucks, 30 drivers, 8 agents; 300 ± 80 LRs a working day, 15 % walk-ins, 2 % cancelled,
  60 % with charges, 30 % with wasuli; 92 % loaded on memos of 10–60 LRs within 2 days; 1 % of memos edited later
  (Differs), 0.5 % cancelled; wasuli 80 % collected; LR edits 3 %. Prints a summary (counts, file size, minutes taken).
- Output kept outside the repo; a copy can be opened with `BM_DATA_ROOT` like the other throwaway roots.

**Budgets (from the Build Plan; measured, not guessed)**
| Action | Budget |
| --- | --- |
| Type-ahead suggestions | < 50 ms |
| Save LR | < 150 ms |
| Dashboard open (summary + pending by station + recent) | < 300 ms |
| Create memo with 100 LRs | < 300 ms |
| Any report, first page, one year | < 1 s |
| Firm statement, one year, biggest firm | < 1 s |
| History, default filter | < 300 ms |
| Ctrl+K search | < 100 ms |
| App start to usable (keeper already running / cold) | < 5 s / < 10 s |
| Hourly backup of the full file | runs without blocking saves for > 1 s |

- `scripts/bench.cjs`: runs each action against the seeded file through the real keeper over HTTP, 20 runs each,
  prints median and worst, and a table PASS / FAIL against the budgets. Writes `docs/bench/<date>-<machine>.md`.
- Anything over budget: find the cause (`EXPLAIN QUERY PLAN`, `performance-optimization` skill), fix it with an index
  (a new migration, never edit an old one) or a query change; re-run the bench. No caching layers, no denormalised
  totals, unless a measured number still fails after indexing — then ask the owner first.

**Stable speed tests (the 4.1 / 4.2 flakes)**
- Wall-clock asserts in `npm run check` (`reports.dbtest`, `history.dbtest`, others): keep them as **guards with a wide
  margin** (e.g. 5 × the measured median, warm-up run first, best of 5) so a busy PC cannot fail them; the real budget
  numbers live in the bench, which is run on purpose, not on every check.

**Database health at size**
- After seeding: `PRAGMA integrity_check`, file size, WAL size after an hour of saves, `VACUUM` time (do not run it
  automatically; record the number). Backup + restore of the full file timed.

**Release 0.3.0** (sessions 4.1 + 4.2 in it): version bump, `npm run release`, and the owner publishes and updates the
installed app **through Settings → Software update** — the first in-app update signed with the new key.

## Out of scope
Changing features, UI polish, the audit scans (4.4), the pilot (4.5).

## Done when
1. All tests pass inside `npm run check`, run alone, three times in a row (no flaky timing failure).
2. The seeded 3-year database exists, `integrity_check` = ok, summary recorded.
3. `docs/bench/<date>-<this PC>.md` shows every budget PASS on this PC (or the owner accepted a named exception).
4. Owner: 0.3.0 published; the installed app updated from Settings (Admin PIN) with no signature error; Components card
   absent in the installed build.
5. Owner, on a real NComputing seat (AnyDesk): copy the seeded file to a throwaway root there, run `bench` (or the
   owner's hand timings from the checklist the session prints), record `docs/bench/<date>-ncomputing.md`.
6. `HANDOFF.md` updated; changed files listed with one suggested commit message, the worktree steps (commit and
   confirm before removing — never `--force`), then `git push` and `gh run list --limit 3`.

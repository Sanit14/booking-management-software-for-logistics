# Session 3.4 — plan (Wasuli: agents, collections, assign / collect / undo)

Status: **waiting for approval — no code written.** Card: `docs/sessions/3.4.md`.

## Primary goal
An admin sees every LR that carries a wasuli amount as a collection to follow up, hands a batch to a collection agent, records what the agent
brought back (Cash / UPI / Card, part payment, remark), and two seats can never both collect — or both undo — the same LR.

## Phase 2 — Wasuli follows the LR (keeper, same transaction)
**How this serves the goal:** the list is only trustworthy if an LR edit, cancel or restore can never leave it wrong, or change money already collected.
- New `keeper/wasuli.ts`: plain functions used inside the LR transactions — save with wasuli > 0 → `unassigned` row; edit that changes the amount → row updated; to 0 → row removed; cancel → unassigned / assigned row removed;
  restore → row back as unassigned; one audit row each (`wasuli.create|update|remove`, entity `wasuli`). A **collected** row blocks an LR edit that changes its amount and any cancel: new refusal `lr-wasuli-collected`
  (detail = LR number; wording "Wasuli already collected for LR n — undo the collection first"). The check runs before the LR is written (nothing half-saved).
- `lrs.ts` calls them from `create` / `update` / `cancel` / `restore`; the routes in `server.ts` also publish `'wasuli'` when a wasuli row was touched (small flag on `LrSaved` / `LrUpdated`, `wasuliPaise` on the others).
- Tests (`wasuliSync.dbtest.ts`): create with / without wasuli; edit up, down, to 0, from 0; edit of other fields leaves the row alone; collected row blocks an amount edit and a cancel, writes nothing; an unrelated edit of a collected
  LR still works; cancel then restore; a zero amount never makes a row; audit rows; refusal leaves LR and row unchanged; event flag only when a row changed.
- Verify: `npm run check`.

## Phase 3 — Transitions and reads (keeper, compare-and-set)
**How this serves the goal:** assign, collect and undo must be exact and race-proof, and the lists must be fast at 20 000 rows.
- `makeWasuli(pins, now)` in `keeper/wasuli.ts`; routes `/wasuli/list|find|agent-stats|assign|reassign|to-pool|collect|uncollect|remark`; bridge handlers, preload, `KeeperApi.wasuli`, types (`WasuliRow`, `WasuliPage`,
  `WasuliCursor`, `AgentStat`, codes `wasuli-stale|missing|invalid`, `master-busy`), `strings.result` wording.
- Each change = ONE `IMMEDIATE` transaction; the claim is one `UPDATE … WHERE id AND status AND agent_id IS ? AND version` and `changes` must equal the rows sent (assign takes a batch, all or nothing, ≤ 500). A moved row →
  `wasuli-stale` with the current rows (state, agent, seat: "Already collected on PC03"), nothing written. Audit row + one `['wasuli']` event per committed change; none for a refusal or a no-op. The row's `seat` /
  `updated_at` are the last change.
- Collect: amount (1 paise … the wasuli amount, defaults to all), mode required, remark optional ≤ 200, date = keeper's today; no PIN. Undo and "edit a collected remark": System PIN (checked first); undo → back to Assigned to the same
  agent, collected fields and remark cleared. Reassign / to-pool: no PIN. Deactivating an agent that still has assigned rows → `master-busy`.
- `list(tab, agentId, period, cursor)`: Unassigned oldest LR first, Assigned oldest assigned first, Collected newest first (7 / 30 days); 100 a page by keyset; count + sum for the whole filter and the three tab counts in the
  same answer; days waiting in SQL. `agentStats` = one `GROUP BY` (assigned count / amount, collected today / period). `find(no)` = this year's LR, else last year's.
- Tests (`wasuli.dbtest.ts`): every transition and its refusals, PIN first and wrong PIN writes nothing, part payment, bounds, undo, remark, double send of one collect = one change, audit and one event per change, list order /
  paging across 1 January / totals / period edges, agent stats, `EXPLAIN` (no scan of `lrs`), speed over 20 000 rows. `server.test.ts`: **two seats collect the same row at once → one `ok`, the other `wasuli-stale` naming the
  seat**; assign of overlapping batches; no PIN / remark text in `keeper.log`.
- Verify: `npm run check`.

## Decisions I need you to confirm (defaults I will take if you just say go)
1. **Agents, the card contradicts itself:** it gives `name_key UNIQUE` *and* "same rules as drivers" (same name + different phone is only a warning). Both cannot hold. Default: keep `name_key UNIQUE`, so the same
   name twice is refused whatever the phone (the pickers and lists identify an agent by name); a similar name still asks for confirmation.
2. **LR edit with collected wasuli:** the card says the edit is refused. Default: refused only when the edit **changes the wasuli amount** (cancel is always refused); fixing a name or a particular still works.
3. **Deactivating an agent who still has assigned collections is refused** ("reassign or send them back first"), because the picker lists active agents only and the rows would be stranded. Not on the card (DM has the same rule for removing an agent).
4. **Collect bounds:** more than 0 and at most the wasuli amount; undo returns the row to Assigned (same agent) and clears mode, amount and remark of that collection (the audit log keeps them).
5. **Dashboard "Wasuli pending" count: not built** (the card says "if it fits"; the Dashboard is full at 1024×768 and it needs another summary query). One line to add later.
6. **Index:** `(status, agent_id, collected_date)` instead of the card's `(status, agent_id)`, so "collected by this agent in the last 7 days" never walks the agent's whole history; `(collected_date)` kept.
7. **Quick collect by LR number** finds this year's LR first, then last year's (as Ctrl+K does).

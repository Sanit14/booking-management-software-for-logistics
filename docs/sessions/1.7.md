# Session 1.7 — PINs, GitHub and in-app updates

## Goal
1. The app gets its two PINs (set once on first run, stored hashed, checked only by the keeper).
2. The code lives on GitHub with a check run on every push.
3. A new version can be published and installed from inside the app, safely, by the owner only.

Pattern to read (not copy): DM's `electron/updater.cjs`, `electron/process-scan.cjs`, `scripts/update-keygen.cjs`,
`scripts/sign-release.cjs`, `.github/workflows/` in `C:\Users\HP\Desktop\dm - auto update\dr-testing`.

## Before the session (owner)
- Create GitHub repo **`Sanit14/BookingManager`** (private, empty) and push `main`:
  `git remote add origin https://github.com/Sanit14/BookingManager.git` then `git push -u origin main`.
- Create GitHub repo **`Sanit14/BookingManager-releases`** (public, empty). Only installers go here, never code.
- Install the GitHub CLI (`winget install GitHub.cli`) and run `gh auth login` once.

## Decided rules for this slice
**PINs (keeper owns them)**
- Two PINs, 4 digits each:
  - **System PIN** (daily gates): LR edit/cancel/date change, move LR off a memo, memo recalculate.
  - **Admin PIN** (owner): updates, PIN changes, backup/data folder changes, restore outside safe mode.
- First run (no PINs stored): before the shell, a one-time setup screen sets Admin PIN then System PIN (each
  typed twice) and shows a **recovery code** once (12 characters, grouped, "write this down"). Set-once is
  enforced by the keeper: if another seat finished first, this seat just continues.
- Stored in `settings` as salted `scrypt` hashes (Node 16 `crypto.scrypt`), never the PIN itself. Recovery code
  stored the same way. No PIN, seed or default anywhere in the code (DM's hardcoded `MASTER_SEED` lesson).
- Checking happens **only in the keeper**: a gated route takes the PIN in the same request and refuses on a wrong
  one. 5 wrong tries for a PIN kind → that kind is locked for 60 s (per keeper, logged). The screen only collects
  digits (PinDialog from 1.5).
- Settings → "PINs" card: change System PIN (needs Admin PIN), change Admin PIN (needs current Admin PIN),
  "Forgot PINs" (recovery code → set both again → new recovery code shown). Every set/change/reset writes an
  audit row (never the PIN). `KEEPER_VERSION` bump.

**CI (checks only)**
- `.github/workflows/check.yml`: on every push to `main`, `windows-latest`, Node version as on the dev PC,
  `npm ci` → `npm run postinstall` → `npm run check` → `npm run dist`. No secrets in CI, no publishing from CI.

**Releases (local, signed, owner publishes)**
- `npm run update:keygen` (once): Ed25519 key pair; private key to
  `C:\Users\HP\BookingManagerKeys\update-signing-private.pem` (never in the repo, never on the client PC);
  public key written into the app source. Refuses to overwrite an existing key.
- `npm run release`: `check` → `dist` → sign the installer's checksum file with the private key → prints the
  exact `gh release create v<version> --repo Sanit14/BookingManager-releases <files>` command. The owner runs it.
- The app refuses any update whose signature doesn't verify with the built-in public key.

**Updater (Settings → "Software update" card; electron-updater, DM's exact version, generic provider →
`https://github.com/Sanit14/BookingManager-releases/releases/latest/download/`)**
- Nothing checks for updates at start or on a timer. Only the button talks to the internet; the app windows stay
  offline (CSP unchanged).
- Steps, each logged to `%ProgramData%\BookingManager\logs\updater.log`, any failure stops with a clear message
  and changes nothing:
  1. Check → "Up to date" or "Version X available" → Download (checksum + signature verified).
  2. Install asks the **Admin PIN** (verified by the keeper, not the screen).
  3. Refuse while another seat has the app open: the keeper's list of seats seen in the last 45 s (from the
     15 s watchdog pings) **and** a Windows process scan across sessions (DM's `process-scan` idea).
  4. Verified backup now (keeper route).
  5. Keeper clean stop, wait until its process has exited.
  6. Install and restart (Windows asks for permission).

## Tests
- Keeper (`*.dbtest.ts`): set-once (second set refused), wrong PIN refused, lockout after 5 and release after
  60 s (fake clock), recovery resets both and issues a new code, hashes never equal the PIN, audit rows written.
- Pure: signature verify (good / tampered file / wrong key / empty key = refuse), seat-list "others online" logic,
  process-scan grouping (fake process rows).

## Out of scope
Using the System PIN on real actions (2.3 onwards), code signing of the .exe (Windows SmartScreen warning is
accepted for now), auto-checks for updates.

## Done when
1. Fresh data folder → first-run PIN setup → recovery code shown once → shell. Second seat (or second start)
   never sees setup again.
2. Settings: change System PIN (with Admin PIN), change Admin PIN, recovery reset — all work; wrong PIN ×5 locks
   for 60 s.
3. Repo on GitHub; the `check` workflow is green on `main`.
4. Release proof on the dev PC: 0.1.0 installed → `npm run release` builds **0.1.1** → owner publishes it →
   Settings → Check → Download → Install (Admin PIN) → app restarts as 0.1.1 with data intact and a fresh
   backup in the backup folder.
5. A tampered or unsigned release is refused with a clear message.
6. `HANDOFF.md` updated; changed files listed with one suggested commit message and the worktree merge steps.

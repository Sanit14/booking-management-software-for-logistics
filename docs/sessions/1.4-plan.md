# Session 1.4 — plan (backup, restore, damage check)

## Primary goal
A damaged or deleted `booking.db` shows a clear restore screen instead of a dead app, and the clerk gets back to
the last hour's bookings by picking a verified backup. No day's bookings are lost to a crash or bad disk.

## Phase 0 — facts checked (no docs to fetch; the API is in the pinned types)
- better-sqlite3 12.11.1: `db.backup(destFile, { progress })` returns a **Promise** (async), `progress(info)` returns pages per step so
  inserts can interleave (`@types/better-sqlite3` index.d.ts:87, 145). `new Database(f, { readonly, fileMustExist })`. Errors are `SqliteError` with `.code`.
- Garbage bytes make `openDatabase` throw at `journal_mode = WAL` (SQLITE_NOTADB). Today that is `keeper-fatal`, exit 1 → becomes safe mode `damaged`.
- Today `server.ts` is fully synchronous in the listen callback and `stop()` is synchronous. `db.backup` is async, so startup and stop become async;
  health gets a state `starting` (the bridge waits while `starting`).
- This worktree has **no `node_modules`**: `npm install` first (needs the short path / VS Build Tools, see HANDOFF).

## Assumptions (veto any)
1. **Backup folder** = `BM_BACKUP_DIR` (dev/tests) → `settings.backupDir` → `D:\BookingManagerBackups`. A damaged db can't be read for settings, so it uses the default.
2. **Pre-migration backup fails** (e.g. no D: drive) → migration still runs, failure logged and shown as `backups failing`. Blocking would leave the app dead on a machine without D:.
3. **Start-up backup** only if no backup file dated today (card wording); the first one is taken *before* the keeper reports `ready`, so the status line is right on first view. Hourly timer + clean stop as the card says.
4. **Restore routes refuse outside safe mode** (`not-in-safe-mode`); the engine itself handles a live db with rows so 4.2 can reuse it.
5. Backups use local time in the file name; "48 hourly" = newest 48 files (start/stop/pre-migration backups count).
6. Clean-stop backup makes `/shutdown` slower (the client waits 3 s); fine for a small db, noted in HANDOFF.

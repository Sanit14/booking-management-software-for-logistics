# Session 4.3 plan — load test, budgets, stable speed tests, release 0.3.0

## Primary goal
The owner can see, with numbers, that Booking Manager stays fast with 3 years of data (~330,000 LRs) on this PC and can repeat the same measurement on a real NComputing seat; the `npm run check` timing tests stop failing by chance; and 0.3.0 is ready to publish.

## Phase 0 — Facts found by reading (no new APIs invented)
**How this serves the primary goal:** the seeder and bench must call what exists, so every call below was read in the code.
- Keeper factories take an injectable clock and PIN checker: `makeLrs(pins, masters, now)` (keeper/lrs.ts:142), `makeMemos(pins, now)` (memos.ts:207), `makeWasuli(pins, now)` (wasuli.ts:131). A fake `now` per simulated day means `date: null` = that day, so **no System PIN (scrypt ~170 ms) per backdated save**; a PIN stub (`verify` → ok) covers edits and cancels.
- `writeAudit` stamps `at` with SQLite's real time and `audit_log` refuses UPDATE by trigger (migrations.ts:148). History reads by `at`, so the seeder must backdate audit rows: drop the two triggers (their SQL read back from `sqlite_master`), `UPDATE audit_log SET at` per simulated day, put the triggers back. Nothing reads `created_at` / `updated_at`, so those stay.
- Tests run under Electron-as-node (`scripts/test-db.cjs`); keeper test harness `startKeeper` (server.test.ts:49): `ELECTRON_RUN_AS_NODE=1`, `PROGRAMDATA`, `BM_BACKUP_DIR`. `scripts/` is not linted and not packaged.
- Likely slow spots to MEASURE, not assume: `makeBackup` verifies the copy with a synchronous `quick_check` on the keeper's thread (backup.ts:35-67); start-up runs `quick_check` + a full `COUNT(*)` before "ready" and a whole-file backup first if none is dated today (server.ts:193-237).
- Stop hook runs `npm run check` in this worktree; the worktree had no `node_modules` → `npm ci` + `npm run postinstall` (started).

## Phase 1 — Seeder
**How this serves the primary goal:** without a realistic 3-year file there is nothing to measure.
- `scripts/seed-load.cjs <root> [--end date] [--days n] [--per-day n] [--app <dist-electron dir>]`; re-launches itself under Electron-as-node; exports `seed()`.
- Through the keeper's own `create/update/cancel/assign/collect` functions, one transaction each, `synchronous=OFF` on the seeder's connection only. Fixed PRNG seed. Shape exactly as the card (400 firms, 40 stations, 60 trucks, 30 drivers, 8 agents; 300 ± 80/day; Sundays light, Diwali weeks heavy; 15 % walk-ins, 2 % cancelled, 60 % charges, 30 % wasuli; 92 % loaded in memos of 10–60 within 2 days; 1 % of memos get a later LR edit (Differs), 0.5 % cancelled; 80 % of wasuli collected; 3 % LR edits before loading). One firm is much bigger than the rest (the "biggest firm").
- Refuses `C:\BookingManagerData` and any folder holding `booking.db`. Seeded PINs Admin 1111 / System 2222 (throwaway data only).
- At the end: checkpoint, `integrity_check`, counts, file size, minutes, `VACUUM` time on a temp copy → `<root>\seed-summary.txt` + console.
- `--app` lets the seat run it from the installed app (`…\app.asar\dist-electron`) instead of copying ~0.5 GB over AnyDesk.
- Test: `keeper/seedLoad.dbtest.ts` — a 10-day, 15/day seed: counts, XOR / status invariants, audit `at` backdated and ordered, triggers back, `integrity_check` ok, same seed twice → same business rows.

## Phase 2 — Bench
**How this serves the primary goal:** it is the instrument that says PASS/FAIL against each budget, here and on the seat.
- `scripts/bench.cjs <root>`: Node built-ins only (runs under the installed exe on the seat). Copies the root to a temp root, starts the real keeper (random port, own `PROGRAMDATA` / backup dir), 20 runs per action over HTTP, median / worst, PASS/FAIL, writes `docs/bench/<date>-<machine>.md` (machine specs + seed summary + table). Exit 1 on FAIL. Not part of `npm run check`.
- Rows = the card's table: type-ahead (`/masters/all` + the screen's ranking function when the repo is present), save LR, Dashboard (3 reads), 100-LR memo (ids from `/memos/pending`), each of the 7 reports + a row's LRs (one year), biggest firm's statement (found via firm-wise report; also the whole account-open as an extra row), History default, Ctrl+K search (LR no., firm prefix, "traders"), keeper cold start to ready and warm "first screen" data, hourly-backup test (`/backups/export` while saves loop: worst save latency must be < 1 s), plus restore timed, WAL size after the save burst.
- Honest limits written into the file: OS cache is warm after the copy (not a reboot-cold start); the Electron window's own start is hand-timed once and noted.

## Phase 3 — Measure, then fix what fails
**How this serves the primary goal:** "stays fast" is only true where every budget passes.
- Seed, bench, read the numbers. Anything over budget: `EXPLAIN QUERY PLAN` (`performance-optimization`), then an index in a **new migration v4** or a query change, with an EXPLAIN / speed test; re-bench. Bump `KEEPER_VERSION` only if keeper behaviour changes.
- Checkpoint: if the cause is backup verification or start-up checks (behaviour of backups / safe mode), I show you the number and the proposed fix **before** changing it. Caches or stored totals → ask first (card rule).

## Phase 4 — Stable speed tests
**How this serves the primary goal:** Done-when 1 is "three clean checks in a row".
- Measure each wall-clock guard (dashboard, firmAccounts, history, memoEdit, memos, print ×2, reports, search, wasuli, server.test save/list timings) on this PC (temporary logging in `fastest`), then set the limit to max(old, 5 × median); keep best-of-5. Real budgets live in the bench. EXPLAIN tests stay as the structural proof.

## Phase 5 — Release 0.3.0 prep and hand-off
**How this serves the primary goal:** the owner publishes and updates from Settings.
- `npm version 0.3.0 --no-git-tag-version`. I do **not** publish and do **not** run `npm run release` here: a release must match pushed code (decision 2026-11-04), so the owner runs it from the main folder after commit / merge / push. HANDOFF gets the exact PowerShell steps, the NComputing checklist (copy or seed on the seat, run bench or hand timings), `docs/decisions.md` lines, `docs/bench/<date>-<pc>.md`, file list, one commit message, worktree steps.

## Phase 6 — Verification
- `npm run check` alone, 3 times in a row, exit 0 (no seed / bench running meanwhile). Seeded DB: `integrity_check` ok. Bench file with all rows PASS (or a named exception for you to accept). Mutation check: drop an index in a scratch copy → the guard / EXPLAIN test still fails.
- Anti-patterns: no generic query endpoint, no changed old migration, no caching or denormalised totals without asking, no git commit / push, nothing touching DM's port / root, nothing in `build.files` shipping the scripts.

## Out of scope
Feature changes, UI polish, audit scans (4.4), pilot (4.5), publishing, owner steps 4–5 of "Done when" (they need the published release and the seat).

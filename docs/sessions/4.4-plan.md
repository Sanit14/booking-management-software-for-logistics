## Phase 0 — Facts found and baseline
**How this serves the goal:** the stall fix must change the right lines, and "green" must mean something before I touch anything.

What the code does today (read, not assumed):
- `keeper/backup.ts:119` `listBackups` opens **every** backup and runs `quick_check` (via `readSummary`, `:13`) on the keeper's thread. `server.ts:496` calls it.
- `keeper/restore.ts:66` `previewRestore` = `readSummary(backup)` + `readLive(dbPath)` (a `quick_check` of the live file too), both on the thread; `verifyApply` (`:83`) does both **again**; `server.ts:386` (`restoreLive`) and `:533` (safe mode) call them.
- `restoreFiles` (`restore.ts:99`) is synchronous: 2–3 `copyFileSync` of the whole file, and `swapIn` (`server.ts:335`) then calls `openChecked(dbPath)` with the **full** `quick_check` (16 s on the 3-year file). That is the rest of the 55 s restore: the keeper answers nothing for that long.
- The child-process pattern exists: `verifyBackup` (`backup.ts:40`) + `verifyChild.ts` (it already prints the whole `DbSummary`, `verifyBackup` throws all but the row count away). Test pattern: `backup.dbtest.ts:186` (20,000-row file, event loop keeps ticking).
- Waits for a clean stop: updater `stopKeeper` (`electron/updater.ts:218`) = `/shutdown` with 10 s timeout, then 10 s for the pid; the launcher's "replace an older keeper" (`keeperBridge.ts:101`) = 3 s timeout + 40 × 150 ms. The bench measured clean stop 6.7–16.4 s. Nothing kills the keeper; a timeout aborts the update (`keeperStuck`, `strings.ts:900`). A manual install over a running keeper is not the updater's path (see Not now).
- Env test hooks: `BM_DATA_ROOT` (`dataRoot.ts:38`), `BM_BACKUP_DIR` (`server.ts:101`), `BM_PIN_LOCK_MS` (`:108`), `BM_MARKER_REFRESH_MS` (`:65`). A packaged keeper reads them from the user's environment.
- Window/IPC already looks right on first read (`main.ts:23` sandbox + contextIsolation, named `ipcMain.handle`s, keeper binds `127.0.0.1`, host check, CSP in `index.html:5`); the security scan confirms or finds otherwise.
- This worktree had **no `node_modules`**: `npm ci` + `npm run postinstall` first. Baseline: `npm run check` once, expect 318 node + 316 database + 59 Electron.
- `README.md` is empty; `HANDOFF.md` is 647 lines.

Allowed building blocks (all exist): `verifyBackup`/`verifyChild`, `makeTokens`, `openChecked(path, full)`, `fs.promises.copyFile`, `fastest(n, fn)` in `keeper/testing.ts`, `leaks()` in `server.test.ts`, bench `timed()`/`call()`/`ok()`. No new dependency.

## Phase 1 — The stall fixes (test first, then code), `KEEPER_VERSION` 19
**How this serves the goal:** this is the goal's first half: no save or ping held up while backups are listed, previewed or restored.

Tests first (each fails on today's code):
1. `backup.dbtest.ts`: `listBackups` lists a good and a damaged file by name / time / size and opens neither.
2. `restore.dbtest.ts`: `previewRestore` and `verifyApply` are async and the event loop ticks while they run (the 20,000-row pattern); a damaged backup is still refused; a live file that is damaged / missing still reads as such.
3. `restore.dbtest.ts`: `restoreFiles` async; the copy is verified before the rename (a copy cut short is refused, the live file untouched).
4. `server.test.ts`: a second `/restore/apply` while a swap is running is refused; `/health` answers during the swap.

Code (smallest change):
- `keeper/backup.ts`: one `summarizeInChild(file) → Promise<DbSummary | null>` (the spawn code moves out of `verifyBackup`, which becomes a 3-line user of it). `listBackups` returns name / time / size only.
- `shared/keeper.ts` `BackupInfo`: `damaged` and `summary` go. `src/BackupPicker.tsx`: the count and status columns go (the compare card already shows the counts); one "Checking the backup…" line while the preview runs (it now takes seconds on a big book). Strings in `strings.safeMode` only.
- `keeper/restore.ts`: `previewRestore`, `verifyApply`, `readLive` use `summarizeInChild` (backup and live **in parallel**); `restoreFiles` copies with `fs.promises.copyFile`, verifies the `.restoring` copy in the child, then renames.
- `keeper/server.ts`: `await` the above in `/restore/preview`, `/restore/apply` (both paths), `restoreLive`; `swapIn` async with `state = 'starting'` while it runs and a `swapping` guard; after the swap `openChecked(dbPath, false)` (the exact bytes were just verified in the child). `KEEPER_VERSION` 19.
- Waits: one constant `KEEPER_STOP_WAIT_MS = 60_000` in `electron/watchdog.ts`, used by `updater.ts` (shutdown timeout and pid deadline) and `keeperBridge.ts` (replace loop); `keeperStuck` string says "a minute". Nothing is ever killed.
- `scripts/bench.cjs`: a saver (`/lrs/create`) and a pinger (`/health` every 100 ms) run while `/backups/list`, `/restore/preview` and `/restore/apply` run; new rows "Saves / health pings while backups are listed | previewed | restored", budget 1 s worst; the old "listing opens every backup" line is replaced. Run it **before** the fix (evidence, saved as `docs/bench/2026-11-0x-…-4.4-before.md`) and after, on `C:\bmload`.

Anti-patterns: no generic query route; no `quick_check` on the keeper thread; no new env switch; `restoreFiles` never overwrites the set-aside copy (`COPYFILE_EXCL` stays); the guard marker still says "running" until a clean stop.
Decisions taken (veto at approval): (a) the list shows no counts / damaged flag — the card allowed "without checking"; counts and "damaged" come with the preview; (b) "no request over 1 s" is measured as: every request is **answered** within 1 s — a save in the 2–5 s swap window gets an immediate "no database" refusal (the book is closed on purpose; other seats were already refused); (c) if the bench shows the preview over ~30 s, the live side switches to the keeper's open handle (counts only) — measured, then decided.

## Phase 3 — Fix High and Medium (and small Lows)
**How this serves the goal:** a finding that is only written down protects no one.

Per finding: a test that fails before (EXPLAIN test for a lost index, a dbtest for a rule, a server test for a route), the fix, `npm run check`.

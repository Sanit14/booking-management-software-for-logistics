# Session 3.1 plan — Loading Memo (create)

Card: `docs/sessions/3.1.md`. Mockup: `docs/design/A-Memo.dc.html`. DM's `ChallanHeader.tsx` (read for behaviour only): DM types the
challan number from the paper and has no claim guard, so nothing to copy; our header is the card's.

## Primary goal
The loading clerk ticks the pending LRs for one truck, fills truck / driver / hire / hamali, presses F4 and gets a challan
number — and no LR can ever end up on two memos, even when two seats save in the same instant.

## Phase 0 — what exists (read, nothing to build)
**How this serves the goal:** it fixes what we reuse, so nothing is re-invented.
- Schema v1 already has `memos` (frozen columns, `UNIQUE(challan_year, challan_no)`, `uid`), `lrs.memo_id`, the CHECK
  `(status='loaded') = (memo_id IS NOT NULL)`, `counters('challan')` and the index `lrs_pending(status, to_station_id, lr_date)`.
  **No migration.** Contingency: if `pending` over 20 000 LRs misses 100 ms, add version 2 with `lrs(status, lr_date, lr_no)` (never edit v1).
- Reuse: `nextNumber('challan', date)`, `writeAudit`, `pins.verify`, `localDate`/`isDate`/`MAX_PAISE` (export it) in `lrRules.ts`, `parseRupees`,
  `lrAmounts` (the oracle in tests), `Stop`/`refuse` pattern from `lrs.ts`, `makeEvents`, `useKeeperData`, `Table`, `TypeAhead`, `Field`,
  `Dialog`, `PinDialog`, `useEnterToNext`, `matches(keys.saveLr)`, `formatPaise`, `isoToDisplay`, the Jump/pick machinery of 2.5.
- `db.transaction(fn).immediate()` exists in `@types/better-sqlite3` 9.6.0. The keeper handles one request at a time (synchronous
  better-sqlite3), so "same moment" is serialised; `IMMEDIATE` is for the card and for a future second writer.
- Dashboard `memos` / `trucksOut` SQL already reads the `memos` table and the page already refetches on `memos`: only a test and the
  removal of "Coming in 3.1." are needed there.
- Worktree has no `node_modules`: `npm install && npm run postinstall` is running in the background (needed before any `npm run check`).

## Phase 1 — Fix the flaky PIN test (first, as the card says)
**How this serves the goal:** a green `npm run check` must mean something.
- `keeper/pins.dbtest.ts` "what is stored is a salted hash…": drop the `includes('1111'/'2222')` and recovery-code substring checks on a random hex
  string. Assert instead: every stored value matches `scrypt1$salt$hash`, **is not equal to** the PIN / code, and `Number(value)` is NaN (does not parse as it).

## Phase 2 — Keeper: memos (test first)
**How this serves the goal:** numbering, the claim guard and the frozen totals are the business rules; they live only here.
- `keeper/memoRules.ts` (+ `memoRules.test.ts`, pure): `asMemoInput(body)`, `cleanMemo(input, today)` → per-field errors
  (`date date|future`, `truck`, `driver`, `fromStation`, `toStation required|same`, `truckHire`/`loadingHamali amount`, `lrs required|many`), money via `parseRupees` ≤ `MAX_PAISE`,
  LR ids = unique positive integers, 1–500; `asPendingFilters(body)`.
- `keeper/memos.ts` (+ `memos.dbtest.ts`): `makeMemos(pins, now)`:
  - `defaults(db, date)` → `{ today, nextNo }` (the screen takes the booking station from the existing `lrs.defaults`).
  - `pending(db, filters, cursor)` — `status='booked'`; filters: from / to date, To station id, consignor, consignee (firm id → `consignor_id = ?`; walk-in text →
    `consignor_id IS NULL AND consignor_name = ? COLLATE NOCASE`); `ORDER BY lr_date, lr_no`, keyset cursor `{date, no}` via `(lr_date, lr_no) > (?, ?)`, 100 rows + `next`;
    plus `COUNT(*)` and `SUM(qty)` of the whole filter from SQL.
  - `totals(db, ids)` — the live panel numbers: LRs, qty, to pay, paid over the ticked ids that are still `booked` (SQL; the screen adds nothing).
  - `create(db, seat, input)` — same `uid` → the first memo (before validation or PIN). Else clean → date ≠ today needs the System PIN → **one `.immediate()` transaction**:
    truck / driver active, from / to stations active (and different), ids all exist → `nextNumber` → INSERT memo → claim `UPDATE lrs SET status='loaded', memo_id, version+1, updated_at WHERE id IN (…) AND status='booked'`;
    `changes < count` → `Stop`: rollback (no number used) and `memo-conflict` with `taken[]` = each LR's number, state (loaded / cancelled) and its memo's challan no + truck →
    **freeze** `frozen_lr_count / qty / topay / paid / charges / stax` in one SQL `UPDATE … FROM` the claimed rows (`charges` = bhada + insurance + delivery + hamali + pf; `stax` = per-LR `(freight*bp + 5000)/10000`, the SQL twin of `taxPaise`) →
    audit `memos.create` (id, challan no, header, LR ids, frozen) → commit. Server publishes `['memos','lrs']` only after `ok`.
  - `get(db, id)` — header, names, frozen totals, its LRs (`LIMIT 500`, by `lr_date, lr_no`). `byDate(db, date)` — that day's memos, `challan_year DESC, challan_no DESC`, `LIMIT 200`.
- `keeper/search.ts`: a digits-only text also looks up `(challan_year, challan_no)` this year then last → `answer.memos` (`LIMIT 5`, index SEARCH).
- Tests (dbtest): each filter and combined, order, cursor across pages, whole-filter totals; create happy path (status, `memo_id`, **frozen = sum of `lrAmounts` of its LRs** across several tax rates and odd paise,
  challan no per year and the 1 January reset, audit row, event); refusals write nothing and burn no number (no LRs, 501 LRs, inactive truck / driver, missing To, From = To, negative / bad money,
  future date, other date without PIN, wrong PIN); claim guard (already loaded → whole save rolled back and names LR + challan + truck; cancelled LR can't be ticked in; mixed good + taken → none loaded);
  same uid twice → one memo; 500-LR memo ok; `EXPLAIN QUERY PLAN` (no `SCAN lrs`); summary counts / trucks out move with real memos; `pending` over 20 000 LRs < 100 ms and a 100-LR save < 300 ms (`fastest(5)`).

## Phase 5 — Loading Memo page
**How this serves the goal:** the clerk does the whole job from the keyboard on one 1024×768 page.
- `src/loadingMemo/LoadingMemoPage.tsx` (+ `.module.css`): filter bar (Booked from / to as `type=date` that follow oldest-pending / today while untouched, To station, Consignor, Consignee TypeAheads, Clear filters) →
  pending table with a tick column (Space = tick the focused row, click / Enter too, Ctrl+A ticks all shown, Ctrl+Shift+A unticks all, `#E3F3F2` tint, "Load more" while `next`) → memo panel.
  The list is fetched as `useKeeperData(…, ['lrs','memos'])` over the pages loaded so far, so another seat booking an LR does not collapse a list the clerk has scrolled.
- `src/loadingMemo/MemoPanel.tsx`: Challan "Next: n", date (+ System-PIN unlock, the small pattern copied from `LrForm`), Truck, Driver, From (booking station), To (follows the filter's station until picked),
  Truck hire ₹, Loading hamali ₹, live totals from `memos.totals`, "Create memo (n LRs)" on the seat's `saveLr` key (Enter on the last box too; ignored while a dialog is open), the "another seat" note,
  one-line "Today's memos" strip (newest few, "+n more"; a click opens the memo). After a save: toast "Challan 13 saved · 11 LRs", ticks and panel clear (date and From kept), focus back to the filters.
  `memo-conflict` → a `Dialog` naming each LR ("LR 245 was just loaded on challan 12 · MH 29 BE 1234"), those LRs unticked, nothing saved.
- `src/loadingMemo/MemoView.tsx`: a saved memo read-only (header, frozen totals from the keeper, its LRs); Esc / "Back" returns to the panel with the ticks intact.
- `src/ui/Table.tsx`: optional `onRowToggle` (Space on a focused row). `App.tsx`: `pageOf` for the new jumps, render the page; `DashboardPage`: station rows activatable → `onMakeMemo(stationId)`, drop "Coming in 3.1.".
- `src/strings.ts`: `strings.memo`, the three result codes, search group; `GlobalSearch` row for a challan.

## Out of scope

timers (the Dashboard keeps its old-day counts after midnight until the next event) · a shared date-unlock hook (copy the 20 lines; extract if a third place needs it).

## Choices I made where the card is silent or loose (say if you want any different)
1. **Layout stacked as the mockup** (filter bar, pending table, memo panel under it), not "left / right": a 9-column table plus the panel does not fit in the 788 px beside the sidebar (same call as 2.2). The page header is dropped, as on LR Entry, to leave room for the "Today's memos" strip; measured at the end (≥ 7 table rows, no page scroll).
2. **Ctrl+K order is LR, then Challan.** "4" + Enter must keep opening LR 4. So "13" shows *LR 13* then *Challan 13*: ↓ Enter opens the memo. Challan-first would break LR search.
3. **The claim does not overwrite `lrs.seat`** (the card lists `seat` in the UPDATE). 2.3's edit / cancel leave it as the booking seat; the memo's own `seat` and the audit row say who loaded.
4. **From = To is refused**, as for an LR (the card does not say).
5. **Space / Ctrl+A / Ctrl+Shift+A are list gestures** like ↑ / ↓, fixed on this page, not entries in the per-seat keymap (Ctrl+A is a reserved key there). The Save key is the existing `saveLr` action (F4).
6. A memo may be dated before one of its LRs (backdate with the PIN); not blocked, the card says nothing.
7. `totals` counts only ticked LRs still `booked`, so the panel never adds the money of an LR another seat just loaded; the save then stops and names it.

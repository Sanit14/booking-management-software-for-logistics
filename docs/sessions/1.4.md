# Session 1.4 — Backup, restore and damage check

## Goal
No day's bookings can be lost to a crash, a bad disk or a deleted file. The keeper makes verified backups on
its own, checks the database at every start, and a damaged or missing database leads to a clear restore
screen instead of a dead app. (DM's July data-loss recovery was done by hand; this makes it a button.)

## Decided rules for this slice
**Backups**
- Made by the keeper with SQLite's online backup (`db.backup()` in better-sqlite3), safe while seats write.
- When: **every hour** while the keeper runs, on **clean stop**, and **before any migration** runs on an
  existing database (so a bad future migration can always be undone).
- Where: `settings.backupDir`, default `D:\BookingManagerBackups`. If that folder can't be created or written,
  the keeper keeps working and reports `backup: failing` with the reason (status line shows it). No fallback to
  the C: drive: a backup on the same disk as the database is not a backup.
- Name: `booking-YYYYMMDD-HHmm.db`. Write to a temp name, verify, then rename, so a half-written file never
  looks like a backup.
- Verify every backup: open it read-only, `PRAGMA quick_check` = `ok`, read its business-row count. A failed
  backup is deleted and logged, never kept.
- Keep the last **48 hourly** backups plus the first backup of each day for **30 days**; prune the rest after
  each new good backup. Pruning never deletes the newest good backup.
- Each successful backup is one line in `keeper.log`.

**Start-up check**
- Every start runs `PRAGMA quick_check` before migrations. Not `ok` → safe mode `damaged` (nothing migrated,
  nothing written).
- Safe mode (from 1.2/1.3 or `damaged`) never leaves the keeper dead: it stays up and serves `/health`,
  backup listing and restore only.

**Restore**
- `backups.list()` → newest first: file, time, size, schema version, counts (LRs, memos, masters), newest LR
  date, last LR and challan number per year. Read-only opens; a file that fails `quick_check` is listed as
  damaged and can't be chosen.
- `restore.preview(file)` → that summary next to the live database's summary.
- `restore.apply(file, confirmToken)` — the token comes from the preview, so the screen must show the
  preview first. In one step the keeper: stops taking writes, checkpoints and closes the live file, copies it
  to `booking-before-restore-<time>.db` in the backup folder (never deleted by pruning), copies the chosen
  backup into place, reopens, runs migrations, updates the blank-database marker, resumes.
- Refused with a clear reason: a backup with 0 business rows when the live database has rows (unless the
  live database is the damaged/missing one), a backup with a newer schema than this keeper, a damaged backup.
- Bump `KEEPER_VERSION` (new routes).

**Screens (plain, unstyled — design comes in 1.5)**
- **Safe-mode screen:** what happened (from the reason code), the backup list, choose one → preview side by side
  → "Restore this backup". All text in `src/strings.ts`.
- Status line adds "last backup HH:mm" or "backups failing: <reason>".
- One "Export backup to…" button: folder picker → a fresh verified backup written there (for the USB copy).
- Restore from normal mode (not safe mode) is **not** exposed yet; it arrives with Settings behind the admin
  PIN (Session 4.2).

**Named routes only**, as before; the preload gets `backups.list`, `restore.preview`, `restore.apply`,
`backups.exportTo`.

## Tests
- Database tests (`*.dbtest.ts`): backup while 500 inserts run in a loop → backup passes `quick_check` and
  holds a consistent count; temp-name-then-rename (no partial file visible); backup before migration exists
  after a migration runs; pruning keeps 48 hourly + 30 daily and always the newest (given a list of fake
  file times); `quick_check` failure on a file of garbage bytes → safe mode `damaged`; list marks a damaged
  backup unusable; preview counts match the files; apply swaps the file, keeps `booking-before-restore-*`,
  reopens and migrates; refusals: empty backup over a live database with rows, newer schema, damaged file,
  wrong confirm token.
- Unwritable backup folder → keeper keeps running and reports `backup: failing`.

## Out of scope
Normal-mode restore and its PIN (4.2), automatic copy to USB, backup settings screen, styling (1.5),
installer folder permissions (1.6).

## Done when
1. All tests pass inside `npm run check`.
2. `npm run dev`: status line shows a backup time within a minute of start (first backup on start if none
   today); the file is in `D:\BookingManagerBackups` (or the reason it couldn't be written).
3. Stop the keeper, delete `booking.db`, start the app → safe-mode screen → pick a backup → preview → restore →
   app back to "Keeper connected · schema v1".
4. Stop the keeper, overwrite `booking.db` with a few random bytes, start → "damaged" safe mode → restore works.
5. "Export backup to…" a folder writes a backup that opens and passes `quick_check`.
6. `HANDOFF.md` updated; changed files listed with one suggested commit message and the worktree merge steps.

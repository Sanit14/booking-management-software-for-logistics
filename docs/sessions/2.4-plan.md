# Session 2.4 — plan (waiting for approval)

## Primary goal
A clerk can book an LR from any page without losing their place (F2 → type → F4 → Esc), set their own keys on their
own seat, never lose a half-typed LR by moving around the app, and see at least 8 of the day's LRs at once on LR Entry.

## Phase 0 — what I read (no external docs; everything is in this repo)
Read: `CLAUDE.md`, `HANDOFF.md`, `docs/decisions.md`, card 2.4, `src/App.tsx`, `src/keymap.ts`, `src/lrEntry/{LrForm,LrEntryPage,LrActions}.tsx`
+ `LrEntryPage.module.css`, `src/shell/{Sidebar,SettingsPage,LrDefaultsCard,Page,pages}`, `src/ui/{Dialog,Button,Toast,Field.module,Card.module}`,
`src/logic/lrOpen.ts`, `electron/{main,preload,keeperBridge}.ts`, `shared/keeper.ts` (`KeeperApi`), `tsconfig.node.json`.

Facts the plan rests on:
- `App` renders pages with `page === ...`, so leaving LR Entry **unmounts** `LrForm` and loses everything typed. The form state, `uid` and
  `manual` set all live in `LrForm` `useState`.
- `KEYS` is a constant in `src/keymap.ts` (`saveLr` F4, `newLr` Escape), used in `LrForm` (window keydown) and as the Save button's key cap.
  `LrActions` hard-codes `strings.ui.esc`. Sidebar Quick LR button just toasts "coming in 2.4".
- `LrForm`'s window keydown ignores keys while *any* `dialog[open]` exists — that would also silence the form inside the Quick LR dialog,
  and a form under the dialog would otherwise also react to F4.
- `Dialog` is fixed 440 px wide, children mount only while open, a modal `<dialog>` sits above toasts (known issue since 1.5 / 2.1).
- `seat.json` lives in `app.getPath('userData')` (per Windows user = per seat); `electron/*.test.ts` already run under `node --test`.
- `tsconfig.node.json` compiles `electron keeper shared src/logic` only → pure code must live in `src/logic/` to be tested.
- This worktree has no `node_modules`: first step is `npm install` + `npm run postinstall` (5–12 min, see HANDOFF).

Not allowed / anti-patterns: no keeper route, no database for keys or drafts, no `localStorage` for keys (it must be the seat file in main),
no hard-coded key strings left in components, nothing newer than Chrome 108 (no Popover API for the toast fix).

## Phase 1 — Shortcut core (pure, test first)
*Serves the goal:* every later phase asks this one "which key means what".
- `src/logic/keymap.ts` (replaces `src/keymap.ts`): actions `saveLr F4, newLr Escape, quickLr F2, goLrEntry F3, goLoadingMemo F5,
  goDashboard F1, focusLrSearch Ctrl+F`; `parseKey` (F1–F12, Ctrl+/Alt+ letter or digit, `Escape` only as a default), `reserved`
  (Alt+F4, Ctrl+W, Ctrl+R, Tab, Enter; I also add Ctrl+C/V/X/A/Z so nobody breaks copy-paste — say if you do not want this),
  `eventToKey` (by `e.code`, so layouts/AltGr do not confuse it), `matches(key, event)`, `checkChange(keys, action, key)` →
  ok | invalid | reserved | `{used: otherAction}`, `sanitize(raw)` (corrupt or partial file → defaults), `keyLabel` (`Escape` → `Esc`).
- Tests `src/logic/keymap.test.ts`: allowed/refused keys, reserved, duplicate names the other action, event → key → action, sanitize.
- Done: `npm run check` green.

## Phase 2 — Seat key file and the screen's key store
*Serves the goal:* keys are per seat, apply at once, hints follow them.
- `electron/seatKeys.ts` (no `electron` import): `loadKeys(dir)` / `saveKeys(dir, keys)` → `keys.json` next to `seat.json`; reads via `sanitize`,
  refuses an invalid set. Test `electron/seatKeys.test.ts` with temp dirs: round trip, missing/corrupt file, **two dirs = two seats stay apart**.
- `main.ts` IPC `seat:keys-get|set`, `preload.ts` `window.bm.keys`, types in `shared/keys.ts` (+ `global.d.ts`). No keeper change, no `KEEPER_VERSION` bump.
- `src/useKeys.tsx`: provider loads once at start; `keys`, `change(action, key)`, `reset()`; `App` wraps the shell.
- `App`: one window keydown for `quickLr`, `goLrEntry`, `goLoadingMemo`, `goDashboard`; ignored while any dialog is open or while Settings is capturing a key.
- Settings → `src/shell/KeysCard.tsx` "Keyboard shortcuts": action, current key, **Change** (press the key; Esc cancels; refusals say
  "Already used by: …" / "Not allowed"), **Reset to defaults**. Strings in `strings.keys`.
- Every hint (Save button cap, New LR cap, Quick LR button, tooltips) reads `keyLabel(keys[...])`; `src/keymap.ts` removed.

## Phase 3 — Drafts and the leave guard
*Serves the goal:* a half-typed LR survives a trip to Settings.
- `src/logic/drafts.ts` (pure, module-level Map in screen memory only): `keep(slot, {state, uid})` (only when something is typed — same test as
  today's `holding`), `load`, `clear`; slots `lrEntry` and `quick`. Test `drafts.test.ts`: keep/load, blank form removes the draft, slots independent, clear.
- `LrForm` (new-LR mode only): starts from the slot's draft (state + uid), writes it on change, clears on a successful save. Saved LR in edit mode never writes one.
  `LrEntryPage` clears the slot when "New LR" is pressed or another LR is opened after "Discard what is on the form?".
- Leave guard: `LrEntryPage` tells `App` when it is **editing**; changing page (sidebar or a key) then asks "Discard changes?" (Keep working / Discard).
  Half-typed *new* LRs do not ask — they are kept.
- Not kept: the PIN-unlocked backdate (the PIN is never stored); the form comes back with today's date.

## Phase 4 — Quick LR dialog
*Serves the goal:* F2 from anywhere books an LR and Esc puts the clerk back.
- `Dialog` gets `wide` (≈ 820 px) and an `hideActions`-style way to show no footer button; `src/lrEntry/QuickLr.tsx` = `Dialog` + the same `LrForm`

## Phase 5 — LR Entry layout (needs your decision, see below)
*Serves the goal:* the day's list shows ≥ 8 rows.
Numbers at 1024×768: main area 736 px tall (16 px padding each side). Today: page header 64 + gap 14 + form ~358 (+50 strip when an LR is open) +
gap 12 → the list card gets ~180 px = 3 rows. Eight rows need ≈ 346 px (table header 34 + 8 × 34 rows + one 40 px strip) even after trimming.
So the form + everything above must fit in ≈ 380 px **including** the action buttons and error lines.
What gets that without breaking the 17 px / 46 px / 14 px floors:
1. No separate page header on LR Entry. The form card gets a head row (44 px): "LR Entry · New LR · next no. 1249" or "LR 1248 · status · Edit / Cancel LR / History / New LR" — this is the card's "action strip in the form header".
2. Form rows: A = LR no, Date, From, Consignor, Consignee · B = To, Particular, Qty, To pay, Paid · C = Option, 4 charges, Wasuli · D = Tax, amounts, Save. Enter order unchanged.
3. "Add to firms" tick moves to the label line of the party box (today it reserves 24 px under it); "Next: 1249" and the date hint go to the head / tooltip (hints under boxes make row A 94 px).
4. List card: its head (chips, day box, Today, LR-no. search) joins the bottom totals strip, rows 34 px (15 px text kept; only this table via a local `--row-h`).
5. Errors: red box + message under the box as today, but if that pushes the list below 8 rows I show the messages as one line next to Save instead (decided when measured).
Measure in the browser pane (as in 2.2/2.3) for: new LR, LR open, five error lines. Honest risk: with several error lines under boxes it can land at 6–7 rows; the one-line fallback above fixes that.
The card's alternative (list beside the form) does not work here: at 788 px wide the form column would be ~376 px, ~10 rows of 70 px = 700 px > 736, so it scrolls and the list is too narrow for 6 columns.

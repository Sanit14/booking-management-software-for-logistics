# Session 3.4 — Wasuli (collections), v1 = DM's page on LRs

## Goal
Every LR with a wasuli amount becomes a collection to follow up. As in DeliveryManager, a collection sits in an
**Unassigned** pool, is **assigned** to a collection agent, and is **collected** (amount, Cash / UPI / Card,
remark) or sent back. The booking-specific rules are still to be decided (spec), so v1 copies DM's behaviour
and nothing more.

Look first (behaviour only, do not copy code): DM `src/pages/Wasuli.tsx` (tabs Unassigned / Assigned /
Collected, agent picker, collect dialog with Cash / UPI / Card + remark, reassign, back to pool, undo collect,
"Collected" period week / month, the 15-row cap with "View all", the in-flight guard against a lagging seat
collecting one row many times), `electron/keeper/engine.cjs` `wasuliTransitionSync` (compare-and-set
transitions).

## Decided rules for this slice
**Migration v2 (first migration after v1 — never edit v1)**
- `agents(id, name, name_key UNIQUE, phone, active, …common columns)` — collection agents. Masters page gets a
  fifth tab **Agents** (same rules as drivers in 2.1: duplicate name+phone refused, similar name confirm, System
  PIN to edit/deactivate, no delete).
- `wasuli(id, lr_id UNIQUE → lrs, amount_paise, status IN ('unassigned','assigned','collected'), agent_id → agents
  NULL, assigned_date, collected_date, collected_paise, mode IN ('cash','upi','card') NULL, remark, …common
  columns)`; indexes `(status, agent_id)`, `(collected_date)`.
- The migration creates a wasuli row for every existing non-cancelled LR with `wasuli_paise > 0`.
- The usual pre-migration backup (1.4) runs automatically. `KEEPER_VERSION` bump.

**Keeping wasuli in step with the LR (keeper, same transaction as the LR change)**
- LR saved (2.2) with wasuli > 0 → an `unassigned` row. Edited (2.3): amount changed on an unassigned/assigned row
  → amount updated; set to 0 → row removed (if not collected); a **collected** row is never changed by an LR edit
  (the edit is refused with "Wasuli already collected for LR n — undo the collection first").
- LR cancelled → its unassigned/assigned row removed; refused if collected (same message). Restored → row back
  as unassigned.
- One collection per LR. Zero-amount LRs have no row (DM's zero-amount bug cannot happen: no row is ever
  expected for 0).

**Transitions (compare-and-set, like DM)**
- `wasuli.assign(ids, agentId)`, `reassign(id, agentId)`, `toPool(id)`, `collect(id, amount, mode, remark)`,
  `uncollect(id)`, `remark(id, text)`. Each sends the state it saw (`status`, `agent_id`, `version`); if the row
  moved meanwhile → refused with the current row ("Already collected on PC03"). One transaction + audit row +
  event `['wasuli']` each.
- Collect: amount defaults to the full wasuli amount, may be less (part payment is recorded as collected with
  the lower amount — DM behaviour); mode required; remark optional. Collected date = today.
- No PIN for assign / collect (daily counter work, as in DM). **Undo collect** and **edit a collected remark**
  need the System PIN.
- Same request twice in flight for one row → the second is dropped (DM's 33-times bug).

**Reads**
- `wasuli.list(tab, agentId, period, cursor)` — Unassigned (oldest LR first), Assigned (by agent, oldest assigned
  first), Collected (by agent, last 7 or 30 days, newest first); 100 per page, keyset; totals for the whole filter
  from SQL; LR number, date, consignor, consignee, To, challan (if loaded), amount, days waiting.
- `wasuli.agentStats()` — per agent: assigned count / amount, collected today / this period. One `GROUP BY`.
- Dashboard (2.5) stays money-free: add only a count "Wasuli pending" if it fits, no amounts.

**Screen — Wasuli page (sidebar, Admin group)**
- Agent picker at the top (TypeAhead over active agents) with each agent's pending count.
- Tabs Unassigned · Assigned · Collected with counts. Table as DM's (LR no., date, consignee, To, challan,
  amount, days). Unassigned: tick rows (Space / Ctrl+A) → **Assign to <agent>**. Assigned: row actions
  **Collected** (dialog: amount, Cash / UPI / Card, remark; Enter flows, F4 saves), **Reassign**, **Back to pool**.
  Collected: **Remark**, **Undo** (PIN). Period week / month on Collected.
- **Quick collect by LR number:** an "LR no." box: type the number + Enter → if it's assigned to the chosen agent,
  the collect dialog opens straight away (DM's fast BS-after-BS entry).
- Totals strip under each table. Fits 1024×768.
- Wasuli print / report: out of scope here (reports 4.1).

## Tests
- Migration v2 from a v1 database with LRs (with and without wasuli) and from empty; backup made first.
- LR create / edit / cancel / restore keep wasuli in step; collected rows block LR edit/cancel; zero → no row.
- Every transition incl. compare-and-set refusals; the in-flight double send → one change; undo needs PIN;
  audit and one event per change, none on refusal; list order / paging / totals; agent stats; EXPLAIN (no scan).
- Real keeper: two seats collect the same row at once → one succeeds, the other sees "already collected".

## Out of scope
Booking-specific wasuli rules (owner decides later), wasuli reports and prints (4.1), Firm Accounts (3.5).

## Done when
1. All tests pass inside `npm run check`; migration v2 runs on an existing 3.3 database with no data lost.
2. Real window: add 2 agents; LRs with wasuli appear in Unassigned; assign 5 to an agent; collect 3 (Cash, UPI,
   part amount with remark), reassign 1, send 1 back to the pool; Undo one collection with the PIN.
3. Edit an LR's wasuli amount → its row follows; try to cancel an LR whose wasuli is collected → refused.
4. Two seats collect the same LR → one wins, the other is told.
5. `HANDOFF.md` updated; changed files listed with one suggested commit message and the worktree steps
   (commit and confirm before removing — never `--force`).

# Session 1.2 — Keeper process and bridge

## Goal
One background **keeper** process per Windows host owns `booking.db`. Every app seat finds it (or starts it)
and talks to it over `127.0.0.1:47715`. The screen shows a live status line proving the chain works:
screen → preload → main → keeper → database.

This is DM's keeper pattern (`electron/keeper/server.cjs`, `client.cjs`, `launcher.cjs`, `bootstrap.cjs`,
`safeguard.cjs` in `C:\Users\HP\Desktop\dm - auto update\dr-testing`) rewritten small in TypeScript.
Read those five DM files for the pattern; **do not copy them**, and do not copy `engine.cjs` or any query shim.

## First: close the test gap from 1.1 (before any keeper code)
`npm run check` must compile TypeScript tests and then run them. Prove it: add one deliberately failing test,
show `check` fails, then delete it. Tests live next to the code as `*.test.ts` under `keeper/` and run with
`node --test` on the compiled output.

## Decided rules for this slice
**Process**
- Keeper source in `keeper/` (TypeScript → CommonJS, Node 16 target, same as `electron/`). Shared request and
  response types in `shared/`.
- Main starts it as `process.execPath` with `ELECTRON_RUN_AS_NODE=1`, **detached**, `windowsHide`, so it
  outlives the seat that started it and serves the others.
- Binds **127.0.0.1:47715 only**. Port already in use → exit quietly (another keeper owns it). That is the
  single-instance rule, so a 9 am rush still ends with exactly one keeper.
- `GET /health` → `{ app: 'booking-manager', keeperVersion, dataRoot, dbPath, startedAt }`. The app checks
  `app === 'booking-manager'`; anything else on that port is an error, never "connected".
- `KEEPER_VERSION` constant shared by keeper and app. A running keeper with an older version is asked to shut
  down (`POST /shutdown`, 127.0.0.1 only) and replaced.
- Launcher in main: ping → if absent, spawn → wait up to 10 s → else show a clear error screen.
  **Never fall back to a local database.**
- Requests are JSON over HTTP POST, one named route each. The preload exposes **named functions only**
  (this session: `keeper.health()`), never a generic `call(route, …)`. Main keeps an allowlist of routes.
- UTF-8 decoded per stream, not per chunk (DM bug: ₹ and Devanagari split across chunks).

**Data root**
- Pointer file `%ProgramData%\BookingManager\root.json`, shared by all Windows users on the host.
  Missing → default `C:\BookingManagerData`, pointer written.
- `BM_DATA_ROOT` environment variable overrides it (dev and tests only).
- Refused roots, with a clear error: a bare drive (`C:\`), anything under a user profile (`%USERPROFILE%`,
  AppData, Desktop, Documents, OneDrive), and anything containing `DeliveryManager`.
  This is the DM per-seat-copy bug; the check is a pure function with tests.
- No UI to change the root in this session.

**Database open**
- `better-sqlite3` **12.11.1** exactly (the version DM runs on the client's Win7 seats), rebuilt for Electron
  22 with `@electron/rebuild` **4.2.0** (postinstall). It is a dependency (runtime), the rest stay devDependencies.
- Open `<root>\booking.db` with `journal_mode=WAL`, `foreign_keys=ON`, `busy_timeout=5000`.
  Create only a `schema_version` table now; real tables are Session 1.3.
- **Blank-database guard:** after the first successful open, write a marker in
  `%ProgramData%\BookingManager\` (one per data root, hash of the root path in the file name) saying a
  database existed there. If the marker exists but `booking.db` is missing or empty, the keeper
  **refuses to create a new one** and reports `{ state: 'safe-mode', reason }`; the screen says so plainly.
- On shutdown (`/shutdown`, SIGTERM, SIGINT): WAL checkpoint, close the database, exit. Failures are logged,
  not swallowed.

**Seat**
- Seat name = the Windows user name by default (each NComputing seat is its own Windows user), stored
  per user in `app.getPath('userData')\seat.json`. Sent with every request as a header. No rename UI yet.

**Logs**
- Keeper appends one line per start, stop, guard trip and error to
  `%ProgramData%\BookingManager\logs\keeper.log`. Plain append, no rotation.

**Housekeeping from 1.1**
- Remove the default File/Edit/View menu (`Menu.setApplicationMenu(null)`).

**Screen**
- The placeholder page gains one status line from `keeper.health()`:
  "Keeper connected · data: C:\BookingManagerData\booking.db · seat: <name> · v<keeperVersion>",
  or the error / safe-mode text. Text comes from `src/strings.ts`. No styling work.

## Tests (node:test, all run by `npm run check`)
- Data-root check: accepted and refused paths, including `C:\`, `C:\Users\x\Desktop\data`, a OneDrive path,
  a `DeliveryManager` path, and `C:\BookingManagerData`.
- Blank-database guard: no marker + no file → creates; marker + file → opens; marker + missing file →
  safe mode; marker + 0-byte file → safe mode.
- Keeper integration on a temp root and a random free port: start → `/health` answers with
  `app: 'booking-manager'` → a second keeper on the same port exits without taking over → `/shutdown`
  closes cleanly and the database file is intact.

1. `npm run check` compiles and runs `*.test.ts`; the failing-test proof was shown, then removed.
2. All tests above pass.
3. `npm run dev`: the window shows "Keeper connected" with the data root, seat and keeper version.
4. Close the app and reopen it: the same keeper is reused (same `startedAt` in `/health`).

   keeper process, shown in Task Manager.
6. With `BM_DATA_ROOT` pointing at a Desktop folder, the app shows the refusal message and creates nothing.
7. Delete `booking.db` after a first run (keeper stopped) and start again: safe-mode message, no new file.
